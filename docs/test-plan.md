# خطة الاختبار - حجوزات الاستراحة

الهدف: التأكد من عدم إمكانية حدوث حجزين متعارضين مهما كان مصدر الطلب أو
توقيته، ودقة عرض التقويم، وسهولة إتمام دورة العمل الكاملة من جهاز هاتف.

## 1. اختبارات آلية (وحدة) - منطق التعارض

الملف: [`src/lib/rental.test.ts`](../../src/lib/rental.test.ts) —
يُشغَّل عبر `npm test` (Vitest). يغطي **القاعدة الأخطر في كامل الوحدة**:
دالة `bookingsOverlap` التي يعتمد عليها كل من التحقق الفوري (API) والتحقق
الملزم عند الحفظ (server actions) وتلوين شبكة التقويم - أي خطأ فيها يعني
إما رفض حجوزات صحيحة أو (الأخطر) قبول حجزين متعارضين فعلياً.

| # | السيناريو | النتيجة المتوقعة | الحالة |
|---|---|---|---|
| ت1 | حجزان منفصلان تماماً بفجوة أيام بينهما | لا تعارض | ✅ مؤتمت |
| ت2 | حجز ينتهي بنفس اليوم الذي يبدأ فيه آخر (تسليم/استلام) | لا تعارض (مسموح تشغيلياً) | ✅ مؤتمت |
| ت3 | تداخل جزئي (نهاية الأول داخل فترة الثاني) | تعارض | ✅ مؤتمت |
| ت4 | حجز قصير محتوى بالكامل داخل حجز أطول | تعارض | ✅ مؤتمت |
| ت5 | فترتان متطابقتان بالضبط | تعارض | ✅ مؤتمت |
| ت6 | التماثل: `overlap(a,b) == overlap(b,a)` | نتيجة متطابقة في الاتجاهين | ✅ مؤتمت |
| ت7 | `isDateWithinBooking`: يشمل يوم الدخول، يستثني يوم الخروج | كما هو موصوف | ✅ مؤتمت |
| ت8 | `nightsBetween`: عدد الليالي = فرق الأيام | حساب صحيح | ✅ مؤتمت |

تشغيل: `npm test` — يجب أن تنجح كل الحالات الثمانية قبل أي نشر للوحدة.

## 3. سيناريوهات إضافية يُنصَح بتنفيذها دورياً (Regression يدوي)

- إلغاء حجز مؤكد ثم محاولة حجز نفس الأيام لعميل آخر → يجب أن تُقبل فوراً
  (الأيام الملغاة تعود متاحة).
- تعديل تواريخ حجز قائم إلى فترة تتعارض مع حجز آخر (غير نفسه) → رفض.
- تعديل حجز دون تغيير تواريخه (تعديل الاسم/الهاتف فقط) → يجب ألا يُرفض
  بحجة "تعارض مع نفسه" (استثناء الحجز الحالي من فحص التعارض عند التعديل).
- التنقل بين عدة أشهر متتالية (شهر بلا أي حجوزات، شهر فبراير القصير) →
  عرض صحيح لعدد أيام الشهر دون خانات زائدة أو ناقصة.
- فتح التطبيق على عرض شاشة هاتف فعلي (لا حاسوب) للتأكد من عدم الحاجة لتمرير
  أفقي وسهولة الضغط على الأيام بإصبع اليد.

## 5. خارج نطاق هذه الخطة

اختبارات الحمل (Load Testing) وتزامن عشرات المستخدمين لحظياً غير ضرورية
لحجم استخدام متوقَّع (استراحة واحدة، موظف أو اثنان) - يمكن إعادة النظر فيها
فقط إن توسّع النظام مستقبلاً لعدة استراحات متزامنة.
